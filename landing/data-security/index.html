Trust / implementation map

Data & security

Security language should match the system that exists. This page maps the current application boundaries without claiming a certification or pretending statement processing stays entirely on-device.

Implementation reviewed: 15 August 2026

The statement-processing path

  1. Authorisation: Google OAuth requests profile access, gmail.readonly and user.birthday.read.
  2. Search: the app searches Gmail for statement-like messages with PDF attachments and stores message ID, subject, sender, date and attachment metadata in Supabase.
  3. Download: matching PDF attachment bytes are downloaded to the running app for processing.
  4. Unlock and extract: the app tries bank password patterns or asks for a statement PDF password, then extracts text from the PDF.
  5. AI parsing: pruned statement text is sent through an authenticated Supabase edge-function proxy to Google Gemini.
  6. Persistence: structured statement, transaction, card and processing-status records are written to Supabase.

Read-only is specific, not invisible

The Gmail scope is read-only: it does not authorise CardCompass to send, edit or delete email. It still authorises the app to search matching mail, read metadata and download a PDF attachment. The current Gmail messages.get call uses the default full format, which retrieves each matching full parsed message into app memory. CardCompass then uses headers and attachment identifiers and does not intentionally persist the message body. The app narrows its query to PDFs and statement-like subjects, but a user should treat connected-statement processing as access to sensitive financial records.

Password boundary

The current UI does not request a full primary account number (PAN), CVV, PIN, OTP or banking password. It can ask for a statement PDF password. A working PDF password and a learned password pattern are cached locally in browser/app preferences, keyed to the bank and user email. The current code does not deliberately send that password to Supabase or Google Gemini.

Local does not mean magically secure. Browser/app preferences are accessible within the local application environment and are not described here as hardware-backed or independently encrypted. Use a trusted device, and clear the site's or app's stored data to remove local password preferences.

Data stored in Supabase

The application attempts to persist profile data including date of birth. If a user-profile row or update is unavailable, DOB may remain in app memory and the product may request it again. Supabase can also hold cards in a user's wallet and last four digits; statement totals, dates, balances and rewards; transactions including dates, amounts, merchant descriptions and categories; Gmail processing metadata; and waitlist applications and consent/attribution fields. Row-level policies are intended to separate signed-in user records, and the public waitlist uses narrow RPCs rather than direct table access.

Legacy card-data capability: the backend schema includes card_number and expiry_date fields, and older RPCs can accept or expose those fields. The current UI does not ask for or send PAN, CVV, PIN, OTP or banking passwords. Removing the legacy storage/RPC capability is a hardening target.

The current statement pipeline processes PDF bytes in the app and does not upload the original PDF file through the repository path. Extracted records remain server-side until deletion or other retention handling applies.

Landing analytics boundary

Plausible requests are transformed before transport. CardCompass removes query parameters and fragments, blanks referrer data, filters event names and retains only placement, step, variant and outcome properties. Form emails, names, spend answers, selected cards and free-text details are not permitted analytics properties. Waitlist attribution is separate: first-touch UTM/referrer-path information can be stored locally and sent to Supabase when an application begins.

Operational controls visible in the codebase

  • Authenticated Gemini proxy requests and a per-user request quota.
  • An allow-list of Gemini model identifiers and a request-size bound.
  • Supabase row-level security for user-owned tables and a protected waitlist operator workflow.
  • Only last four card digits are used in current add-card and statement-matching flows.
  • Input validation and length bounds on public waitlist RPC parameters.
  • Query stripping and property allow-listing at the analytics transport boundary.

What we do not claim

This page is not a penetration-test report, audit opinion or promise that incidents are impossible. CardCompass does not claim an independently audited security or compliance status. Security depends on the application, hosting configuration, providers, user device and continued maintenance. Any material incident or suspected vulnerability should be reported promptly.

Deletion and security contact

The current product does not provide a self-service deletion button. Request deletion of waitlist or product records at support@cardcompass.in. Clear local browser/app data separately to remove cached statement PDF password material. Use the same address for a suspected vulnerability; include reproduction details without sending live secrets, OTPs or full financial credentials.
